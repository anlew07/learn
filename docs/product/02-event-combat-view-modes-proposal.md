# 候选玩法：事件切换地图与幸存者式自动战斗观战

> 用户创意记录 · 2026-11-16 · **仅设计备忘，不参与当前 #51 场景实现、不进入已批准开发范围**。
>
> 参考体验：《Vampire Survivors》战斗构筑与清怪反馈、《Magic Survival》自动技能表现、《WorldBox》观察自主实体、现有《同时穿越》的三波自动战斗。不要把视觉演出当成规则结算。

## 1. 玩家提出的体验

当分身在多世界地图中探索、排险、救援或遭遇特定重大事件，**符合已有战斗条件时**切换到一张短时战斗地图：

- **自动观战**：分身自己移动、释放技能，与敌方交锋；玩家可以观看战斗的全过程，并在现有规则提供可选奖励/战技时自行选择，或者交给自动策略。
- **快速演出（上帝视角）**：以地图总览展示战斗的几个代表阶段，可跳过画面，直接看结果。
- **直接结算**：完全不播放，直接获得同一战斗的结果、资源变化和伤害/危险缓解记录。

玩家的快乐来源不只是「掉一份奖励」，更包括：角色变强后能可视化地面对更多威胁、自动构筑形成明显效果、不同世界出现不同遭遇。**不新增强制的手操战斗**。

## 2. 复杂度判断

| 候选能力 | 开发复杂度 | 为什么 |
| --- | --- | --- |
| 直接结算 + 现有战报 | 低，已有能力 | 保留引擎原战斗与奖励结算 |
| 基于既有战斗记录的可跳过上帝视角演出 | 中 | 需要可靠事件记录、Canvas 回放与生命周期管理 |
| 自动观战：独立地图、角色自动移动、技能特效与敌人集群 | 高 | 需要表现层轨迹系统、视觉资产、性能限制与跨场景恢复 |
| 真正可玩的幸存者式实时战斗（怪物寻路/碰撞/技能命中） | 很高，属于新游戏子系统 | 改动规则确定性、平衡、操作与存档，不应本轮实现 |

**当前决定**：只保存本设计。下一轮应先完成三世界能看懂、能操作的固定 HUD，以及真实世界状态随时间变化的可玩垂直切片。即使只演出三波，也需要先通过实际玩家视觉验收，再考虑增加完整自动战斗地图。

## 3. 最重要的规则约束：一战三种观看方式

1. **唯一战斗结果源**：现有 `src/engine.js`、`src/systems/wave-combat.js` 与 survivor-wave 规则计算一次真实战斗结算；显示模式只读 `lastCombat` / `spectacle` 快照。
2. **不能重复结算**：重看、快进、跳过、刷新、切图、后台恢复和多标签只读页面都不能再支付/奖励或消耗随机数。
3. **表现与规则隔离**：短时自动走位、碰撞火花和飞行道具是由结果快照驱动的视觉重演，**不是第二套战斗命中判定**。不得通过动画持续时间决定伤害或掉落。
4. **奖励选择是规则决策，不是观战奖励**：如果未来提供三选一，必须在规则层产生合法、确定性的待选候选；玩家手选、自动选择都使用同一个引擎命令。跳过动画不等于跳过还需要玩家决定的奖励；若自动选择必须明确以现有策略代选。不能先结算再追加一次奖励。
5. **随时可跳过**：玩家可以切到快速结果，结果与完整观看严格一致；系统异常时优先显示结果/安全返回世界。
6. **H5 轻量与性能**：主地图、战斗地图不要同时跑昂贵动画；仅渲染前台可见场景，减少动态效果时改为静态阶段图；触屏 320px 仍可操作。
7. **自由选择但不打断模拟循环**：战斗展示的入口只在真实发生的战斗或事件中出现，不因为“画面好看”凭空触发新游戏日或全局危机。

## 4. 可复用的当前能力与缺口

| 已有能力 | 可复用方式 |
| --- | --- |
| `lastCombat` 中的 `day`、`stages`、`skills`、`bonus`、`spectacle` | 保存一次战斗的事实，供三种观战模式统一读取 |
| `build.pending` 与已有 `chooseBuild` 合同 | 已有合法战技选择，可作为未来战斗奖励决策入口；**不是战斗每场必掉奖励** |
| 已有固定主场景 Canvas/HUD（#51 Draft） | 前往战斗地图、返回原场景的 UI 容器 |
| 自主策略、重大事件与援助 | 决定何时发生现有行动和事件，而不是由观战画面改写结果 |

尚缺少：统一的只读回放事件时间线、观战/跳过 UI、战斗场景图集、敌方与技能表现、回放性能验证、奖励决策与观战流程的明确边界。这些不应被一个「播放」按钮掩盖。

## 5. 将来可能的最小可行验证（**不在本轮执行**）

只针对灵灾一场**已经完成真实结算**的战斗：

- 从 `lastCombat` 派生 3 个代表阶段、单个分身/威胁、装备技能与结算提示；提供「观看 8–15 秒」和「跳过到结果」。
- 不实现新的寻路、实时伤害或掉落；观战没有任何游戏指令。
- 记录并验证：同一种子同次战斗、完整观看和瞬间跳过，RunState/ProfileState 完全一致；重看 10 次也没有重复奖励。
- 验收玩家是否觉得战斗结果更直观、更爽，且并未感到必须观看动画。若不成立，保留现有战报而不扩张系统。

## 6. 暂不解决的重大问题

- 战斗是**真实幸存者小游戏**还是**可视化演出**？默认后者；前者需要单独用户决策及数值重设计。
- 玩家控制角色移动吗？当前方案**不控制**；由分身自己战斗。
- 允许观战途中选择新战技吗？如果会改变本场结果，属于新的规则时间线，必须由引擎明确支持保存/恢复；现有 `build.pending` 是独立机制，不能直接伪装成中途升级。
- 是否每个事件都能战斗？**不可以**。必须依据已有战斗类型和场景逻辑，不把资源选择/人物剧情硬改成战斗。
- 费用、收益、离线执行及审核文本：在有真实原型和规则依据前不做决定。

> **结论：候选方向保留并可追踪，但本轮不修改战斗结算、奖励规则、存档或用户玩法入口。**
