## 一、现状根因：不是配色，是信息介质错了

截至当前主线，`src/ui.js` 的游玩页仍按照 `controls() → playerGuideHtml() → decisionQueueHtml() → world-map → worldOverviewHtml() → interventionHtml() → footer()` 依次在文档流中排布；`src/style.css` 中 `.app-shell` 是 `max-width:660px; min-height:100vh; padding-bottom:90px`，`.stack` 是纵向块流。

因此即使使用土棕配色、像素资产和四栏底部导航，核心体验仍是：

- 向下滚动寻找某张世界卡和某个按钮；
- 战斗、成长、危机更多由文案告诉玩家，缺乏持续存在的可观察场景；
- 同时展示大量段落和系统细节，像交互式生存报告/网页小说；
- 主要指令和局势不在同一个视野，滚动改变上下文；
- 画面缺少“在这里持续模拟，玩家可随时介入”的空间隐喻。

**明确方向**：停止继续优化旧长卷卡片；主玩法采用固定手机视口的 **HUD + 像素观察场景 + 上下文操作 + 抽屉菜单**。完整故事和历史日志允许存在，但只作为次级内容。

## 二点五、美术品质基准：优先 Dungreed 手机版，次选 Shattered Pixel Dungeon

**用户再次明确（2026-11-16）**：之前提供的固定 HUD HTML 样机「太简陋」。样机仅验证布局与点击逻辑，**不得当作正式像素美术、完成度或最终视觉风格范例**。最高优先的美术参照为 **Team Horay《贪婪地牢》Dungreed 手机版**；技术/工期确实无法达到时，才以 **《Shattered Pixel Dungeon》** 作为可接受的品质次选。

这不是「给网页加像素边框」或「用大色块拼几个营地元素」：

| 美术要素 | 首选：Dungreed 式精细像素场景 | 退而求其次：Shattered Pixel Dungeon 式清晰像素地牢 | 不接受的替代 |
| --- | --- | --- | --- |
| 场景 | 有辨识度的多层地形、墙壁/地面纹理、营火/建筑/环境道具、前中远景层次 | 清晰的像素 Tilemap、房间/路径、地形差异与可读的场景元素 | 纯色背景 + 几个方形框当世界 |
| 角色 | 可分辨的像素分身、装备/动作姿态、受威胁或救援时的状态变化 | 轮廓清楚、风格一致的角色与威胁精灵 | 用单字符、emoji、通用小圆点充当角色 |
| 动效 | 少而精的行走/待机/挥击或救援反馈、命中/状态效果、环境细动效 | 低帧像素动画 + 清晰的事件标记与反馈 | 只有文字滚动，或与状态无关的循环特效 |
| UI 与物件 | 统一像素图标、装备/物资轮廓、带重量感的硬边框 HUD | 统一 Tile/Item/按钮像素尺寸与状态 | 网页卡片、低质 emoji、套色但无美术资产 |
| 色彩/光影 | 每个世界有可识别的主题色、材质层次、受控光影与前景对比 | 有限调色板、明暗分层、保证移动端文字对比度 | 单一深绿/深棕色铺满整个页面 |
| 视觉层级 | **游戏场景必须是主视觉**，HUD 与操作面板贴边 | 地图/场景 + 固定状态/快捷栏 | 大块说明文本占领首屏 |

### 美术制作与开发验收

1. **先做最小垂直切片，而非整游戏换皮**：先完成「灵灾」一个代表性房间/户外场景、1 个分身、至少 2 类环境物件、1 个危机/战斗反馈和完整 HUD 的实际运行画面。让用户在手机截图里确认画面品质，再扩展其他世界。
2. **画面不能靠 CSS 实心色块充数**：至少使用真实的原创像素地形/角色/图标/精灵资源。可复用合法开源素材作过渡，但检查许可证、风格一致性和项目分发权；**不直接复制游戏原作截图、精灵或 UI 资源**。
3. **固定美术语法**：约定基础 tile / sprite 像素尺寸、角色相对场景比例、整数缩放 / `image-rendering:pixelated`、图层顺序、动画帧率和透明像素处理，避免同屏出现不同像素密度和糊边。
4. **轻量且真实**：H5 优先复用压缩的图集、CSS/DOM HUD 与必要的 Canvas 2D 场景绘制；按需绘制和暂停不可见动画，避免为了追求像素精细引入大型引擎。复杂不等于资源体积大。
5. **品质与玩法双重验收**：需有玩家实际看到的世界画面、真实状态驱动的动作反馈、320–430px 适配截图；不能仅用静态 CSS 测试、长文档或占位示意图宣布「像素美术完成」。
6. **当前阶段边界**：用户说「暂且先这样」——本轮仅固定参考标准与验收基准，**不启动大规模代码/素材重做，不合并尚未审定的主 UI 方案**。

官方/实际参考核对：

- [Dungreed 手机版，Google Play](https://play.google.com/store/apps/details?id=com.teamhoray.dungreed)（含游戏截图、环境/角色/装备展示）。
- [Shattered Pixel Dungeon，Google Play](https://play.google.com/store/apps/details?id=com.shatteredpixel.shatteredpixeldungeon)（含实际移动端截图，地图、地形与状态 HUD）。

## 二点六、模拟／放置／经营参考：让场景真正成为游戏，而不是装饰（2026-11-16 补充）

> 用户新增亲身体验过的参考：《天道：创造》（TapTap）、《异世轮回录》、《血色虫灾》、《修仙模拟器》。它们用于明确**玩法感、状态可视化、经营与自动战斗的关联**；《Dungreed》手机版依然是**像素美术品质首选**，《Shattered Pixel Dungeon》是美术次选。**不得把「艺术风格」和「经济／玩法系统」混成单一游戏照搬。**

**名称核对**：用户写「修仙模拟器」，TapTap 存在这个确切名称的轻放置游戏；也存在不同作品《了不起的修仙模拟器》。后续不得自动认定两者是同一款，也不因不确定就强行迁移到重度宗门经营。

### 由这些参考推导的主玩法循环

**观察三个世界正在发生什么 → 调整分身的长期策略或关键资源配置 → 时间自主推进 → 事件与战斗自然发生 → 资源／危机／救援进度和场景状态同时变化 → 结束本局并回看决定造成的结果。**

- **观察**不是看自动刷字：至少让分身动作、场景危机／恢复程度、营地设施或敌情、当前任务位置有**与实际 RunState 有关的不同可见状态**。
- **干预**不等于每日微操：保留现有策略、重大事件、援助和战技选择，在关键节点突出提示；禁止为凑互动而要求每日点五次行动。
- **成长**不是只有数字变大：资源积累、等级／战技提升、救援准备提高，应有简洁可见的阶段反馈与下一步目标；但不虚构不存在的建筑或能力。
- **战斗**不应只是一页文本日志：进入已有三波战斗时，可从真实战斗记录显示参与者／技能／威胁／结果；**动画绝不作为结算依据**，也不额外掉落奖励。
- **长文本**作为「事件细节、人物经历和历史手记」按需打开，不能重新占领主场景。

### 应用到正在进行的 #51 垂直切片

当前 #51（`design/pixel-stage-lingzai-20261116`）已经实现像素遗迹、固定 HUD、世界切换和只读画面模型，但**静态场景 + 有限闪光动画仍不足以验证模拟器体验**。下一轮对 **灵灾** 应先验证以下三类真实状态驱动差异：

1. **平稳／恶化**：危机压力变化能让同一个遗迹呈现可辨认的环境、敌情或营地状态差异；
2. **准备／成长**：分身等级、物资积累或救援准备达到不同阶段，场景能反馈正在准备/防御/救援，而不是只改顶部数字；
3. **决策／后果**：玩家选择策略、援助、事件或战技后，展示**引擎实际产生的结果**，让玩家说得出「我的选择改变了什么」。

通过验收的最低证据：同一世界截取至少三个不同状态的**真实浏览器运行截图**，并有状态→画面映射的单元/浏览器测试。新效果不能使用模拟随机源、绕开引擎或对真实游戏存档造成额外写入；未完成时不宣称「模拟器体验已经达标」。

### 参考游戏的反面教训

- 《天道：创造》玩家评论提到后期重复、成长目标模糊：不能只把生灵／资源／关卡数字刷大，要保留救援任务、失败后学习和世界差异。
- 《血色虫灾》玩家反馈存在图像辨识、升级选项不适配当前构筑及战斗反馈偏弱的问题：角色、弹窗、收益变化必须看得清，选项与玩家当前构筑有关。
- 《了不起的修仙模拟器》复杂系统丰富，但新玩家负担很重：本 H5 不能照搬整个宗门管理深度；优先一个世界、一套清楚的可观察循环。

**这只是源于真实游戏的设计约束和证据清单，不是把新经济、设施、NPC 或离线玩法自动列为已批准需求。**

## 二点七、WorldBox《世界沙盒》：世界必须是能观察的模拟系统

> 新增玩家参考（2026-11-16）：**WorldBox / WorldBox - God Simulator（世界沙盒）**，与《天道：创造》同属宏观世界观察参考，但更强调**可见地图、实体自主行为、时间推移与世界局势联动**。这不是引入「上帝无成本操纵世界」的授权。本项目既定核心仍是有限资源下的救援与分身自主生存。

### 真实产品证据

- [WorldBox 官方网站](https://www.superworldbox.com/)：玩家创造世界，观察不同生物及文明互动和发展，可通过工具影响世界。
- [WorldBox Steam 官方商店](https://store.steampowered.com/app/1206560/)：实体拥有特征与需求，文明自行建立王国、拓展地域，城镇与势力的变化在地图中可见。
- [WorldBox Google Play 手机版](https://play.google.com/store/apps/details?id=com.mkarpenko.worldbox)：居民自行建房、修路、交互，地图与聚落是主要视觉载体；玩家通过工具查看或施加影响。

### 值得移植的三个重点

| WorldBox 体现的体验 | 本项目应该如何体现 | 不应误解为 |
| --- | --- | --- |
| **世界会自己活着** | 分身、敌情、居民／救援活动按现有引擎状态产生不同场景表现；暂停与加速能在主观察区看出来 | 每个 NPC 都要做实时寻路和完整 AI 模拟 |
| **变化可被看到并被记住** | 救援准备提升、危机积压、战斗化解威胁后，地图／营地／区域状态有可辨认的阶段变化；手记提供前后因果 | 每天任意刷随机建筑和无意义装饰 |
| **观察与干预互相连接** | 聚焦某个世界、查看区域或分身状态，使用已有策略／事件／援助干预，随后展示真实的变化回执 | 不花资源随意创造文明、放陨石或删除世界 |

### 与《天道：创造》的区别

- **天道：创造**：侧重宏观规则与世界进化的策略选择——帮助我们回答「玩家决定什么」。
- **WorldBox**：侧重在地图上观察实体、聚落与势力如何随时间改变——帮助我们回答「玩家能看见什么」。
- **本项目**：两者结合但保持末日救援约束：玩家不是无所不能的神，而是管理有限干预机会的守望者。

### 对当前 #51 及后续素材并行的建议验收

先对**灵灾**做轻量的**状态驱动画面分层**，而非立刻造一个 WorldBox 级别的全图模拟引擎：

1. 选一个小范围真实场景：营地／遗迹／危险边界三个视觉区域在一屏中可辨认。
2. 从已存在的 RunState 字段推导「安稳、紧急、正在救援、战斗准备」等少数可靠**表现状态**；如果规则没有该实体，不能在 UI 中假装已经建造某设施。
3. 让角色与场景有**有节制的活动**，暂停时停止；事件、危机、资源和角色成长的反馈必须来自同一份真实状态。
4. 给同一种子、同一日、同一世界两次渲染做一致性测试；**只切换视角或播放画面不得推进天数、消耗随机数、写存档或发奖励**。
5. 用低危机／高危机／已救援或失败三组可复现状态截图验收「肉眼能看出差别」，并记录一次合法玩家决策前后的真实变化。不以动画数量、地图面积或建筑数量作为验收目标。
6. 素材 B 线预备时同时规划**场景状态差分资源**（修复前／修复后、正常／受威胁、空闲／救援活动），不是只生成背景图和独立角色；A 线以图层替换接入，C 线验证性能、手机可见性与游戏状态一致。

**严禁自行加入**完整文明外交、国家战争、无限地图生成、造物／毁灭工具、真实时间挂机经济等与现有玩法无关的大系统。WorldBox 的价值是**世界演变可视化的表现原则**，不意味着复制它的所有模拟机制。


## 三、主界面屏幕合同（竖屏优先）

过去用户确定的目标为 **手机竖屏优先**；Dungreed 的横屏布局只是参照其**画面优先、固定 HUD** 方法。是否增加横屏模式是后续大决策，不从这次反馈擅自推断。

从上到下固定为 5 层，**游玩页整体不可自然纵向滚动**：

```text
┌──────────────────────────────┐
│ DAY 12 | 救援 0/3 | AP 3 | ☰ │ ① 顶部状态 HUD：极简、始终可见
├──────────────────────────────┤
│ [灵灾]   [废土]   [兽潮!]     │ ② 世界切换：三世界真实状态
├──────────────────────────────┤
│  世界像素场景 / 自动行动动画 │
│                              │
│  真实角色、事件/巢群、场景   │ ③ 主观察窗口：主要视觉区域
│  即时变化、关键任务标记     │     不用大段文字卡取代场景
│                              │
│  今日结果一句话 / ! 事件    │
├──────────────────────────────┤
│ 准备 [########  ] 67/100    │ ④ 选中世界状态：2 条关键进度
│ 危机 [####      ] 42/100    │     + 剩余天数 / 关键资源
├──────────────────────────────┤
│ [▶继续] [策略] [援助] [战技] │ ⑤ 主操作 HUD：稳定可点击
│ [战报] [总览] [帮助] [速度] │     次级项可放 ☰ / 抽屉
└──────────────────────────────┘
```

- ③ 推荐成为手机视口中**最大的连续区域**，目标占可用高度 45–60%（视可用高度与系统安全区弹性调整；不是不顾设备强制高度）。
- 主屏顶部绝不堆完整新手说明、大块总目标或日志列表。首次指导可用短浮层/高亮和帮助入口。
- 主世界视角切换是**UI 焦点切换**，不改变世界是否推进；三世界仍同步模拟。
- 世界需要**能读出的状态**：已有世界的成功/失败、危机、事件、战斗结果可用边框、状态标签、轻动画或像素角色变化说明，不必造完整动作游戏。
- 自动事件、战技选择、战报、设置等在遮罩/底部抽屉中呈现，**展开前后主场景位置和世界选择不得跳动**。
- 详细面板可以在自身区域上下滚动；这和把整个游戏主屏做成长网页不同。支持关闭、返回、焦点、长文字、屏幕阅读与大字号。
- 高风险事件需明确「不操作会怎样」；面板不自动改变游戏结算、支付、刷新或存档；最终引擎判定仍是唯一事实。
- 主屏不出现未实装的商城、账号、强化或云存档操作。

## 四、最重要的五条 UI 原则

1. **游戏画面 > 解说文字**：玩家能在场景里观察分身/危机/行动。文字只提供一行反馈或按需展开。
2. **稳定位置 > 长列表**：继续/暂停、速度、世界切换、重要事件入口在熟悉的固定位置；不要求找按钮先滚页。
3. **一个焦点 > 三屏并排卡片**：主视野聚焦一个世界，另两世界用顶部简要风险指示，可一键切换、查看全局。
4. **弹出菜单 > 新的长内容块**：世界详细资料、队伍构筑、战报日志、帮助和设置是独立菜单/抽屉。
5. **先有真实系统 > 再有视觉效果**：像素角色、资源和战斗反馈必须从真实状态驱动，不能只画一张重复播放的假战斗动画。

## 五、技术实现建议（不迁移技术栈）

推荐保留 Vite + 原生 JavaScript + DOM + CSS；主场景绘制可使用**Canvas 2D + 现有 SVG 像素精灵素材**，HUD/按钮/模态仍使用 DOM（方便触控、语义和可访问性）。没有必要为固定 HUD 引入 Pixi/Phaser/React。

建议拆分层次：

- `src/presentation/`：派生当前世界/全局观察模型，复用 B 的纯展示解释与已有 Engine 合同；
- `src/ui.js`：主游戏壳状态（selectedWorldId、activePanel 等）和已有命令分发，不独立模拟世界；
- `src/ui/game-stage.js`（如必要）：从实际 RunState/世界快照绘制像素场景，**展示时绝不使用会改变引擎 RNG 的随机流**；
- `src/style.css`：`height:100dvh` + CSS Grid/Flex 固定主壳，`minmax(0,1fr)` 让场景伸缩；使用 `env(safe-area-inset-*)` 与回退布局；
- 抽屉：有限高度 `overflow-y:auto` + 单独焦点/返回处理；不直接在 body 上复用旧长 `.stack` 结构。

CSS 的 `dvh`、`svh` 和滚动容器原理参考 MDN：https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/length 。子面板滚动与滚动链参考：https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Overscroll_behavior 。不能只给 `body{overflow:hidden}` 就把其他功能裁掉。

## 六、分阶段实施顺序与责任

### R0 · 界面视觉和交互目标（本文件 / 可点击布局样机）

- 现有实现技术审计、参考游戏来源、固定视口 HUD 结构和基本菜单合同。
- 先通过手机 320/375/390/430px 样机检查方向；**样机不是游戏，不能充当功能验收**。

### R1 · 主壳重构（A 主责）

- 将旧的长页游玩主界面改为固定视口主壳、世界切换、可观察场景、暂停/速度、关键资源进度和上下文按钮；
- 旧功能必须从菜单或抽屉仍然可达，不删除事件、策略、援助、融合、战技、战报、教学/结算；
- 使用独立 `design/` PR；不修改存档数据协议、行动结算与随机数规则。

### R2 · 呈现/反馈接入（B 配合）

- 基于现有 `getPlayerGuidance` / Engine preview 合同生成对局、选中世界、事件、技能和一次行动的精简视图；
- 文字控制在主屏一行主要状态和必要风险提示；完整解释留给抽屉；
- 不新增线性小说式长段落，不为了展示而生成新剧情。

### R3 · 可玩性/回归（C 主责 + 总控验收）

- 先改旧 E2E 对新主壳的真实定位器，再覆盖完整第一局、世界切换、策略、援助、事件、战技、结算、存档；
- 联合集成后运行所有 Vitest、Playwright、文本导出/审查、构建、数值回归；
- Android Chrome/iOS Safari/TapTap WebView **需要真实设备证据**，不能用 Chromium 视口冒充。

## 七、阻断式验收标准

1. **主界面不可整页滚动**：在 320×568、320×640、375×667、375×812、390×844、430×932 CSS px 下，`document.documentElement.scrollHeight <= innerHeight + 1`，`scrollWidth <= innerWidth + 1`；不靠裁掉必要操作通过。
2. 首屏就能找到**世界切换、当前危机、救援进度、当前天数、暂停/继续、策略**；弹出层不能阻挡未触发的操作。
3. 进入/关闭战报、帮助、设置、角色、事件时主场景锚点不变，关闭后能返回同一世界和暂停状态。
4. 需要详细阅读的**面板可内部滚动**；中文放大/系统文本缩放后可完整查看，44 CSS px 触控目标。
5. 世界切换不能改变世界日程、AP、RNG 状态；画面动画/战斗重播不能二次加奖励。
6. IndexedDB 写失败、Web Locks 只读和损坏档保护在新 HUD 下依然显著且可靠。
7. 真人首玩不看说明书能说出「自动进行的是分身；自己控制的是策略与关键决定」；不知道怎么操作不得以长教程代替修复 UI。

## 八、参考布局原型与边界

2026-11-16 单独制作了**自包含 HTML 竖屏交互样机**，示意固定 HUD、世界切换、像素观察画面、主操作和底部抽屉；用 Chromium 浏览器做了 320×640、375×812、390×844、430×932 的布局/点击检查，没有主文档溢出。此样机 **不读取真实游戏状态、不提供真实战斗、不写正式存档、未经过 Android/iOS 真机验收**；是否将设计迁移进主游戏需另立实现 PR。

> **质量界限**：像素画面不能替代真正的游戏体验。本次最重要的交付指标是「游戏视图稳定、操作不必找页、不同系统有各自入口」，其次才是增加角色或动画丰富度。
