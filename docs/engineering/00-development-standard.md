## 0.1 事实来源、原则与冲突处理

- `docs/product/00-game-product-blueprint.md` 负责**产品为什么存在、页面该有什么、需求优先级和验收标准**。

- `AGENTS.md` 约束 AI 的仓库定位与不可破坏的不变量；`CONTRIBUTING.md` 记录仓库模块细则、实际命令和贡献行为。
- 当前分支实际源码、自动化测试、CI 和当前用户最新明确指示是事实来源；**规范是约束与目标，不得用文档中计划的功能冒充已完成事实**。
- 发现规范冲突：先验证仓库当下行为 → 在 PR 中指出冲突和影响 → 更新相应文档 → 由总控决定集成。不可暗中选对自己方便的一份。
- 核心原则依次为：**玩家理解与实际可玩性、安全与正确性、可维护性、性能/包体、开发速度**。严禁为了漂亮架构引入没有产品收益的大型迁移。

## 1. 需求进入开发的标准：先定义问题

每项开发任务都需要一条可追踪 Issue/PR 或任务记录，至少包含：

| 必填字段 | 写什么 | 不合格示例 |
| --- | --- | --- |
| 玩家/维护者问题 | 谁遇到什么困难、有何真实证据 | 「感觉功能还不够多」 |
| 用户可观察的目标 | 玩家操作或系统结果如何变化 | 「把界面弄高级一点」 |
| 所属产品模块 | 产品蓝图 S01–S16/具体规则模块 | 「全游戏都改」 |
| 本次范围与不做的事 | 涉及的文件、交互、明确排除项 | 不断扩大到别的功能 |
| 数据与规则依据 | 引擎合同、RunState、ProfileState、配置或内容包 | 从 UI 猜费用或概率 |
| 成功/失败/边界态 | 正常、不可用、失败、重试、刷新时应怎样 | 只做快乐路径 |
| 兼容性与风险 | 存档、随机数、审查文本、移动端与并行修改 | 「应该没影响」 |
| 交付证据 | 测试、截图、PR、CI、部署或人工试玩如何验证 | 「代码写完了」 |

### 1.1 Ready for Development（可开工）

- 有清晰的玩家问题、范围和可观察验收；对未确定的设计以**候选**标注。
- 查过最新 `main` SHA、开放 PR、相关文件与既有实现；没有重复造轮子的理由。
- 判断是否改变核心规则/经济/世界观/存档、引入费用或需要外部权限：**重大决策由用户确认**；小范围实现细节直接推进。
- 明确本轮由 A/B/C 哪条线负责；文件所有权、接口约束可执行。
- 新 UI 没有真实模型时先定义交互和状态契约；不能上一个空按钮当「占位功能」。

### 1.2 不准通过的需求

- 没有玩家问题就添加新功能；把美术图、日志堆叠当作体验改善。
- 未经批准引入**增量挂机、离线收益、账号云存档、全量清档、付费/广告、重大玩法迁移**。
- 为展示三波战斗而增加额外游戏日、重复奖励；为省事让 UI 绕开引擎规则。
- 没有完整存档兼容方案就更改必须字段或自动清除玩家本地数据。

## 2. 标准开发流程（每一项 PR 必须走）

1. **检查事实**：拉取/读取 GitHub `main`、开放 PR、相关代码/文档、运行基线测试。
2. **调研与选型**：优先查官方 API、现有依赖和成熟开源方案；比较维护、包体、许可与回退成本。不要只因为「最新」就换技术。
3. **定义最小变更**：明确输入/输出、调用者、状态与失败路径、玩家可见结果，列出涉及模块。
4. **建立独立分支**：从最新 `main` 建立一项任务对应一个分支/PR；基线记录 commit SHA。
5. **先复现再修复**：Bug 先写可重现的失败用例/截图/种子，确认修复后通过；新功能先测试关键合同。
6. **增量实施**：配置/规则 → 无副作用模型 → UI → 测试/内容导出 → 文档。发现共享接口变更先通知其他线。
7. **本地自查**：静态检查、相关 Vitest、Playwright、生产构建、种子模拟或保存故障测试，根据影响范围选择。
8. **提交 PR**：说明用户问题、实际改变、被影响/未改变的部分、测试证据与遗留风险，不自动合并。
9. **审查与集成**：验证 PR 头提交、CI、冲突及其他并行分支的新变化；按依赖顺序合并，合并一次做一次主线检查。
10. **发布验收**：确认最新 `main` 的 Build/Deploy 真正成功，移动真机与平台发布单独验收；更新任务状态和开发记录。

**不允许**把「已提交」「PR CI 通过」「main CI 通过」「Pages 发布成功」「用户手机能玩」「TapTap 上架」写成一个笼统的「完成」。

## 3. 并行 GitHub 工作规范（最多三条开发线 + 一个总控）

### 3.1 职责与文件归属

| 工作线 | 主责任 | 原则上不改 |
| --- | --- | --- |
| A · 交互/视觉 | UI/DOM、CSS、像素素材、UI 截图和体验测试 | 数值、存档、审核生成器 |
| B · 策划/内容 | 配置/规则、纯展示模型、事件文本、数值测试 | A 的布局样式、C 的存档/审核工具 |
| C · 质量/发布 | 浏览器测试、存档/并发安全、审核脚本、发布验收 | A 的主 UI 和 B 的数值规则 |
| 总控 · 产品/集成 | 需求裁决、产品与工程文档、跨分支接口、最终合并 | 非必要不与 ABC 同时争用核心代码 |

- 独立分支示例：`design/camp-home-yyyymmdd`、`feat/onboarding-yyyymmdd`、`test/mobile-acceptance-yyyymmdd`、`docs/product-blueprint-yyyymmdd`。
- 不允许直接推送 `main`、强推、删除/重写他人的提交，除非用户明确授权且具备恢复方案。
- 只在任务范围里改文件；若 A/B/C 必须同时接触同一文件，先约定**单一修改所有者 + 稳定接口**，另一方通过导出函数/模型/测试配合。
- PR 应尽量小而可审查；庞大模块化重构应分离于玩法、平衡、存档等变更；不采用「一个 PR 顺手修十件事」。
- 发现共享文件改变导致格式检查、CSV 更新冲突：基于最新主线重新生成，再审查 diff，绝不只为让 CI 绿而关闭检查。
- 需要串行依赖时，**先把底层合同/解释数据接好，再修改交互层**，最后运行 C 的联合新手/安全回归。
- 每个子对话结束要提供：分支、PR、头 SHA、文件列表、实际跑过的测试与链接、不可验证的风险。

### 3.3 合并门禁

- [ ] PR 针对最新主线评估，无不可解释的冲突；待合并头 SHA 与已测试 SHA 一致。
- [ ] 执行过受影响模块的正常/失败/边界测试，历史关键流程没有回归。
- [ ] 最新 PR CI 成功；不能用之前某次旧 SHA 的绿色记录顶替当前。
- [ ] UI 变更经过至少 320/375/390/430 CSS px 浏览器检查，截图有来源；测试视口**不等于真机**。
- [ ] 玩法数值调整有同种子前后对照，且区分模拟结果与真实玩家结果。
- [ ] 文案修改同步文本导出与审查；依赖/资源有许可检查。
- [ ] 存档迁移、删除、玩法经济/世界观重大修改已取得必要决策。
- [ ] 影响数据或主路径且无法合理回滚的缺陷已解决；需要人工继续测试的点明确列为遗留。

## 4. 代码架构和长期维护

### 4.1 必须保持的依赖方向

`src/config/*` → 静态数据、可读配置；`src/systems/*` → 规则/无副作用合同；`src/engine.js` → 唯一的局内状态结算与命令边界；`src/presentation/*`（若有）→ 只读/纯派生展示；`src/ui.js` → 显示与用户操作；`src/services/*` → 持久化、独占会话等边界服务。

- **UI 不直接扣费用、修改世界状态、执行第二次结算**。预览结果读取共享纯合同，实际命令再次在引擎校验。
- **规则不能依赖 DOM/浏览器存储**；随机数来自明确的种子流，不读 `Math.random` 代替固定种子模型。
- **显示不能消费 RNG**；同一世界、同样种子、同样操作，结局须一致。
- **专属机制参数统一进入配置**，避免把平衡常数散落在 UI、文本和测试中。
- 新增配置对象有稳定 ID、合法值与默认值；纯函数返回可解释状态，而非产生隐藏全局副作用。
- 选择低耦合的模块边界，**不按固定文件行数机械拆分**；大文件只在实际修改相关领域、已有回归保障时逐步拆开。
- 拒绝未经理由的全新框架、网络后端、自研数据库、自研状态管理；确有收益时在 PR 列出规模、包体/许可证、替代方案和撤回成本。

### 4.2 JavaScript 与 DOM 约定

- 以 ES modules、`const`/`let`、明确命名和小型纯函数为默认；不要新增隐式全局状态或异常吞掉逻辑。
- 同一状态字段只允许一处负责写入，避免 UI 直接操作 `run.worlds`。
- 处理玩家可输入的字符串/事件内容，必须进行安全转义再插入 DOM；不要把外部文本直接拼进 `innerHTML`。优先 `textContent` 和安全 DOM API；既有字符串模板必须复用转义方法并测试。
- 不在 HTML/CSS 里伪造概率、费用、战力、等级或冷却；玩家文本与逻辑键分离。
- 错误分类：用户操作被合法拒绝（说明原因）、暂时性存储/锁失败（可重试/只读）、开发者异常（记录日志/复现信息，不向玩家泄露堆栈和私人数据）。
- 拒绝通过长注释、重复装饰代码、无用抽象来「看起来专业」。

### 4.3 存档与模拟不可变约束

- 每世界每天仅一个主要自主行动；三波战潮属于原有战斗，不产生第二份主要行动和奖励。
- 大事件、终局、援助、融合均按已有资格与费用合同结算；`P100` 不直接等于拯救。
- `applyCommand` 带操作 ID，重复提交不能重复消费/发奖；旧档、刷新和多标签切换按现有幂等语义处理。
- RunState 与 ProfileState 原子批量写入；保存使用命令发生时的快照，串行队列，避免乱序覆盖；写失败暂停推进并保留恢复入口。
- 使用原生 Web Locks 单写者；只读标签页禁止执行写命令，重新获得锁先重读最新已保存状态。
- **存档变更**必须写兼容说明/测试（正常旧档、损坏旧档、缺字段、版本不符、写入失败、强制关闭的局限）；未经批准不可静默清空用户数据。
- 模拟压测不得写入生产用户存档，也不得在运行正式页面时偷偷启用调试速率和测试数据。

## 5. 游戏设计与数值开发规范

任何增加行动、设施、角色、战技、事件或资源的提案，都必须先说明：

1. 它解决哪一段玩家体验问题（难学、无选择、无目标、重复、战斗无反馈）？
2. 玩家在什么时机看到，做什么选择，放弃什么机会？
3. 它与既有行动、资源、危机、终局和跨世界能力是否有重复？
4. 有无强到成为唯一正确答案，或弱到永远不选？
5. 原有三世界不同策略与新手路径是否仍成立？
6. 如何测：固定种子、行动分布、胜率、结束日、资源剩余、事件触发率、战潮收益、触控交互频率？

- 所有新增数值先放入可调配置，设计文档记录取值理由与对照实验；参数变化引用固定种子（如多个策略×世界）比较，不能只报「更爽」。
- 首次玩家需要看到的是结果与代价，不是完整平衡表；深层统计放战报/手记。
- 内容包统一：稳定 ID、触发条件、前置/失效、玩家选择/自动默认、费用/风险、结算、日志、审查标签、测试。
- 只允许在用户明确授权后改变底层经济循环、世界胜负门槛、大范围战斗定义；「增量游戏」仅可选研究，不进入本轮任务。
- 世界观保持开放谜团、救援与重建主题；不要未经授权改成有确定唯一幕后敌人的故事。

## 6. UI / 内容 / 体验工程规范

- **功能优先于装饰**：每个页面要有唯一主要用途，能回答「我是谁/目标/当前情况/下一步」；关键行动不要埋在长日志下面。
- **页面要遵循产品总纲的 S01–S16 功能表**，新增页面前先填写页面需求卡：入口、场景、主要信息、主操作、默认、空态/错误、返回、数据源、测试。
- 全游戏采用一致的低饱和 2D 像素生存 RPG：平涂、有限色板、硬轮廓、整数像素缩放；禁止混入科幻霓虹、玻璃拟态、模糊发光。
- 中文可读性高于像素字体形式，至少检查 320/375/390/430 CSS px、44px 触控目标、对比度、字号放大、iOS/Android 安全区和减少动画偏好。
- **真功能才有真按钮**：设置中的声音/登录/云档/永久加点等若没有系统支持，不出现可点击的假开关。
- 首次教学和解释模型必须可跳过、可复看，不阻断模拟，不悄悄改变世界行动或概率；没有人操作事件时依原合同自动处理。
- 每个重要操作回执解释**已发生的真实状态变化**，不伪装成未来收益承诺。对失败原因无法确定时不猜测。
- DOM/UI 变化需有 Playwright 用户路径测试与截图（截取设备宽度/版本/场景），避免只测样式字符串。截图视觉通过 ≠ 真人能看懂。
- 文案改动执行 `npm run text:export` + `npm run text:check`，动态文案参照 `npm run text:runtime` / `npm run text:review`；人工平台审核不是工具可自动判定。

### 6.1 页面合同的 PR 阻断性检查（2026-11-16）

新增/重构页面除本节原则外，必须核对[页面职责合同与首局教学闭环](../product/04-page-contract-and-first-session.md)；它是产品总纲 S01–S16 的执行层，不另立并行规则。

- **状态和文件归属**：PR 记录 main 基线、相关 Draft PR 和“已有/在做/缺口/候选/暂不做”差异。不能把 Draft 截图、待办或拟议交互写成上线功能；总控更新状态表，不和 UI 分支争用同一源文件。
- **页面职责**：一个主屏一个主要决策，其他能力从次级层可见；运行中的主游戏采用固定 HUD，严禁回到整页长卷。详细抽屉允许内部滚动。首页/结算可以有自己的布局，不机械套用固定 HUD 限制。
- **交互副作用**：仅打开/关闭/切换世界/播放战报不推进模拟、不支付、不二次抽随机数；命令由现有引擎执行。重大事件超时、默认处理、只读与存档失败边界不可被 UI 隐藏。
- **内容可达**：帮助在首页和运行中可达；设置只给真实可用偏好/说明，不能做空按钮；首局聚焦必须能查看仍在运行的第二世界，不得承诺尚未接入的永久升级或云档。
- **验收证据**：新 UI 的截图及主文档滚动检测覆盖 320×568、320×640、375×667、375×812、390×844、430×932；必须记录前后世界、暂停状态、打开/关闭路径、界面截图 SHA。沿用既有自动化流程后，仍需首次玩家理解测试和真机记录，不能以 CI 代替。

## 7. 测试策略和 CI 实际门禁

### 7.1 分层测试

| 层次 | 工具和目标 | 至少覆盖什么 |
| --- | --- | --- |
| 纯逻辑/合同 | Vitest | 正常、无效、边界、费用/冷却、随机种子、终局等规则 |
| 持久化/会话 | Vitest + Playwright | 拒绝读写、超额、损坏档、事务中断、写入后刷新、多标签抢锁 |
| 浏览器流程 | Playwright Chromium | 首页→首局→策略→事件→援助→战斗→结算→重载 |
| 视觉与移动适配 | Playwright/截图 + 人工 | 320–430 px、字号、长中文、键盘、安全区、对比度 |
| 数值/策略回归 | 既有 seeded 脚本 | 各世界/策略胜率、行动分布、失败原因、战潮是否重复结算 |
| 真实体验 | 人类手机试玩 | 看懂目标、找到入口、做出可解释选择、失败后能理解原因 |
| 发布与合规 | CI + 人工 | 静态/运行时文本清单、授权、平台要求、设备适配 |

- Playwright 推荐按玩家可见行为做断言、每条测试隔离存储上下文、优先 `getByRole`/`getByLabel` 和自动重试断言，避免根据偶然 DOM 顺序、固定延迟或脆弱 CSS 猜测结果。
- Bug 修复必须先有复现证据并加入回归；不因样本偶尔红灯就删测试、放宽断言或盲目加重试次数。
- 不能把「虚拟时间运行四小时」当作「真机连续四小时测过」；固定种子模拟胜率不是玩家真实胜率。
- 没有工具或权限导致某层无法验证，必须列为**未验证**并附影响，不得报「全通过」。

### 7.2 与当前仓库一致的命令

当前 GitHub Actions `.github/workflows/ci.yml` 已执行下列链条（并不证明人的检查项被自动执行）：

    npm ci --no-audit --no-fund
    npm run lint
    npm run format:check
    npm run text:check
    npm run text:runtime
    npm run text:review
    npm test
    npm run build
    npm run balance:check
    npm run compare:interventions:check
    npx playwright install --with-deps chromium
    npm run test:e2e

可先运行受影响的最小测试定位，再运行完整流程。仓库 `npm run verify` 不是上述全部命令的完整替代；至少缺少 `text:check` 与审核导出步骤，不能以运行 `verify` 宣称所有审核门禁通过。

- 新依赖必须评估大小、许可证、活跃维护、安全风险和替代方案；同时提交 `package-lock.json`，CI 保持 `npm ci`。
- CI 失败时标记阻断并定位失败的任务/日志；合并前必须验证**最新 PR 头 SHA**。
- CI 绿灯后仍需要主线复测：先确定集成结果，不把多个分支单独通过等同联合通过。

## 8. 真机与发布验收

**阶段 A：PR 提交**：文件与变更清单、测试、CI、截图、审查；不表示已上线。

**阶段 B：集成主线**：关联 PR 按依赖合并，最终 `main` SHA 的全量 CI 成功；核对构建目标基路径 `/learn/`。

**阶段 C：Pages 预览**：最新 SHA 对应的 `Publish H5 preview` build/deploy 成功，独立核查网站可访问及静态资源加载；流程成功不代表用户某部手机可正常操作。

**阶段 D：真实设备**：Android Chrome、iOS Safari，以及适用 TapTap WebView，记录机型、OS/浏览器版本、URL、步骤、截图、设备局限。重点为：刷新/后台强杀、IndexedDB 限制、Web Locks、速度与时间、键盘/安全区、长期耗电/卡顿。未实测的设备不填「通过」。

**阶段 E：TapTap 提审**：按最新官方实际渠道、账号资质、隐私与版权、人工审文、商店素材和后台要求准备；不把 Pages 当 TapTap 上架。

### 8.1 发布阻断问题（P0）

- 数据被静默覆盖/清除，或写失败后继续推进。
- 多标签产生双写，重复支付/掉落/结算；固定种子结果无法重现。
- 新手必经主路径按钮失效、无法从开局到结算、重要事件无法处理/退回。
- 320px 可用布局出现关键按钮被遮挡、文字难以辨认、触控无法点击。
- 主线 CI 最新 SHA 有失败；实际 Pages 最新部署失败却声明「已更新」。
- 提审所需资质/用户隐私/授权要素未核实，却宣布正式上线。

### 8.2 完成的定义（Definition of Done）

一项功能只有满足下列事实时才可以写「开发完成」，并写清**尚未完成的层次**：

1. 需求对照已接受的玩家问题/产品功能规格，实际行为可演示。
2. 改动范围小而可维护，满足规则合同/存档安全/性能限制。
3. 正常、错误、边界有相应测试，CI 与 PR 对应。
4. 页面文字、文档、审核清单和截图（如适用）同步。
5. 已在 PR 记录链接、SHA、实测内容和不能证实的事项。
6. **只有最新主线集成且经验证**才能称「已进入 main」；只有部署/实际访问验证才能称「预览可用」。
7. **只有真机/平台确实实测**才能称「真机验收/正式发布完成」。

## 9. 事故、回归与回滚规范

- 测试失败先记录失败的 `main`/PR SHA、场景、复现步骤、影响范围；确认是代码、环境、测试问题中的哪种。
- 不直接为了恢复绿色而关掉测试或修改校验阈值；必要时暂停下一条 PR 合并。
- PR 尚未合并：在**本任务分支**修复并重新跑 CI；需要集成共性变更则提前通知其他线。
- 已合并且影响线上：优先用安全的独立修复 PR；如需要回滚，先评估是否存在新版存档格式导致旧版无法读取，**不得随意重写 main 历史**。
- 有丢档风险时保护现有 IDB 数据，优先暂停写入/进入只读，不自动初始化空白新局覆盖原档。
- 重大事故记录：时间、影响功能、检测方式、恢复操作、用户可见说明、回归用例和后续预防动作。

## 10. 文档与维护习惯

每次影响玩家功能的改动，要按需要更新：

| 变更类型 | 应更新的文档 |
| --- | --- |
| 新功能/新页面 | [产品总纲](../product/00-game-product-blueprint.md)、需求记录、必要的 UI/内容规格 |
| 核心规则/平衡 | `docs/08-decisions.md`、配置与实验报告、必要的 `CHANGELOG.md` |
| UI 与美术 | 页面说明、风格规范、移动截图和验收记录 |
| 用户文案 | 文本导出和 `docs/review/` 人工复核材料 |
| 存档/权限/部署 | 技术风险、可恢复与验收文档、README/发布清单 |
| 测试与质量工具 | 测试入口、CI 改变、失败处理说明 |

- 新增文档不能复制大量已经存在的维护细则；相互链接和引用规范更利于长期维护。
- 关键决定记录「背景→候选→选中方案→放弃方案→影响范围→验证」，避免新对话一再重复同一争论。
- 发现文档与已验证的代码不符，先在 PR 中修订文档；**不能为对齐过期文档而无理由改坏游戏**。
- 每次完成后向用户简报：**实际修改、真实测试、PR/提交 SHA、Pages 状态、仍待验证**。

## 13. 具体模块合同（旧 CONTRIBUTING 规范的唯一归口）

本附录保留历史贡献规范中仍有效、容易被抽象架构描述遗漏的局部合同。模块名字以最新仓库实际存在的文件为准。

| 模块 | 写入权 / 禁止行为 | 验证重点 |
| --- | --- | --- |
| \`src/config/game-data.js\` | 世界、战技、成长静态定义；不读取运行状态 | ID 稳定、数据完整 |
| \`src/config/balance.js\` | 数值参数唯一来源之一；不持有 DOM/存档 | 固定种子平衡、边界 |
| \`src/systems/action-policy.js\` | 纯策略评分，随机性只走显式 RNG | 不因对象顺序或展示次数漂移 |
| \`src/systems/wave-combat.js\` | 三波战斗表现和封顶修正；不独立扣终局费用、升实际等级或再发一份奖励 | 收益封顶和一次结算 |
| \`src/systems/event-contract.js\` | 事件选项、风险、支付前校验；引擎与 UI 共用 | 失败不扣费、超时默认 |
| \`src/systems/run-metrics.js\` | 只统计真实已结算行动，不制造资源或 RNG | 统计不改变结局 |
| \`src/systems/finale-readiness.js\` | 展示真实终局资格，不能自建第二套通关规则 | P100 未必能获救 |
| \`src/systems/fusion-contract.js\` | 借力资格、费用、供力者去重与冷却合同 | 单人不可重复充当两供力者 |
| \`src/systems/aid-contract.js\` | 实际 P/D 增量、成本、来源材料风险和目标共享冷却 | 封顶有效、无效援助拒绝付款 |
| \`src/systems/strategy-contract.js\` | 长期策略切换免费期、AP 预留、非法状态 | UI 提示和引擎支付一致 |
| \`src/systems/intervention-ledger.js\` | 只记录结算前后**已发生**的差额，不预测、不再执行效果 | 重放/重复命令不新增记录 |
| \`src/systems/crisis-advisor.js\` | 用已存在的合同做纯风险排序和建议，UI 仅导航 | 建议不额外支付或救场 |
| \`src/systems/event-chain.js\` | 两段式事件的排队、一次性标志和每日持续效果 | 稀有线索不阻塞普通主线 |
| \`src/engine.js\` | 独占日推进和最终结算；玩家命令通过 \`applyCommand\` | 指令幂等、同种子可复现 |
| \`src/presentation/*\` | 只读解释与展示派生；不可自动推进、付款、抽 RNG、保存 | A/B 接口与真实合同一致 |
| \`src/ui.js\` / \`src/style.css\` | 可见交互、布局和事件分发；不直接改局内资源 | 操作可发现、视口和无障碍 |
| \`src/services/persistence.js\` | RunState / ProfileState 批量事务读写与串行保存；不持有游戏规则 | 失败暂停、缺失/损坏档、FIFO |
| \`src/services/exclusive-session.js\` | Web Locks 单写者；禁止自研竞争性 localStorage 心跳锁 | 只读隔离、重获锁先读最新 |
| \`scripts/balance-report.mjs\` / \`scripts/intervention-compare.mjs\` | 读取实测结局统计，不重新结算隐藏收益 | 固定种子前后数据复现 |
| \`docs/review/\` / 文本导出脚本 | 与实际玩家文案和动态模板同源，不凭关键词自动宣称合规 | text:check、手工审核证据 |

对新增模块仍按「负责一个明确的状态变化/展示职责、跨边界通过纯合同」设计。没有新增模块需要时，不应机械制造目录。

### 13.1 审查时使用的最小复核表
